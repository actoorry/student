# 微信零钱提现确认收款设计

- 日期：2026-06-26
- 目标：在 `uniapp-marriage` 的提现记录页，为“微信零钱”且处于“待确认/转账中”阶段的提现记录提供“确认收款”入口；用户点击后拉起微信确认收款，并在返回页面后自动刷新状态。

## 1. 背景与问题

当前微信提现自动转账走的是微信商家转账“用户确认收款”模式。后端在微信返回 `WAIT_USER_CONFIRM` 时，会把转账单置为处理中，并在提现详情接口中返回：

- `transferChannelMchId`
- `transferChannelPackageInfo`

但 `uniapp-marriage` 前端尚未消费这两个字段，因此：

1. 用户审核通过后无法在小程序内继续完成“确认收款”；
2. 提现记录只能看到“转账中/审核通过”等状态，无法推进到微信零钱到账；
3. 用户不可能一直停留在申请提现页等待审核完成，必须支持“稍后回来确认”。

## 2. 设计目标

### 2.1 用户目标

用户进入“提现记录”页时，可以直接找到仍需确认收款的微信零钱提现记录，并一键完成确认收款。

### 2.2 业务目标

- 不新增提现详情页；
- 在现有提现记录页闭环完成确认收款；
- 尽量复用现有后端接口；
- 仅在微信小程序内展示/执行该能力；
- 确认完成后自动刷新列表状态，减少“已确认但界面未更新”的困惑。

## 3. 方案选择

### 方案 A：提现记录页直接确认（采用）

在提现记录卡片内展示“确认收款”按钮。点击后拉取该条提现详情，再调用微信确认收款能力，返回后刷新列表。

**优点：**
- 改动集中，开发量小；
- 用户路径最短；
- 不需要新增页面或路由。

**缺点：**
- 列表项逻辑会稍复杂；
- 需要前端维护单条按钮的处理中状态。

### 方案 B：提现详情页确认

记录页仅跳转详情页，详情页负责确认收款。

**不采用原因：**当前需求明确要求直接放在提现记录页，新增详情页会增加路径成本。

### 方案 C：进入记录页自动拉起确认

**不采用原因：**打扰性强，多个待确认记录时行为不可控，不符合当前预期体验。

## 4. 页面与交互设计

目标页面：`UI/uniapp-marriage/pages/distributor/withdraw-record/index.uvue`

### 4.1 卡片展示规则

每条提现记录继续展示：
- 提现标题
- 金额
- 时间
- 状态

在此基础上，若满足以下条件，则额外显示按钮：
- 提现方式为微信零钱（`type == 5`，即 `WITHDRAW_TYPE_WECHAT_API`）；
- 当前记录存在 `payTransferId`；
- 当前状态属于“待确认/转账中”阶段。

前端初步状态识别采用“业务状态 + 渠道信息兜底”的组合策略：
- 列表中先按状态文案/状态码判断是否可能处于处理中；
- 点击按钮后，以详情接口返回的 `transferChannelMchId` 与 `transferChannelPackageInfo` 是否存在，作为最终是否可发起确认的依据。

### 4.2 按钮文案与状态

默认文案：
- `确认收款`

点击处理中：
- `确认中...`

不可确认但数据缺失时：
- 不显示按钮，或点击后提示“当前记录暂不能确认收款，请稍后重试”。

### 4.3 点击后的交互流程

1. 用户点击“确认收款”；
2. 前端调用 `getBrokerageWithdraw(id)` 获取最新详情；
3. 校验以下字段：
   - `transferChannelMchId`
   - `transferChannelPackageInfo`
4. 调用微信小程序 `requestMerchantTransfer` 能力；
5. 用户完成/取消/失败后，前端给出反馈；
6. 前端重新加载提现记录列表，刷新状态。

### 4.4 用户提示

- 若当前不是微信小程序环境：提示“请在微信小程序中确认收款”；
- 若渠道参数缺失：提示“收款参数未准备完成，请稍后重试”；
- 若用户取消：提示“已取消确认收款”；
- 若微信能力调用失败：提示微信返回的错误信息；
- 若调用成功返回：提示“已发起确认，请稍后刷新查看到账状态”或直接刷新后静默展示最新状态。

## 5. 技术设计

## 5.1 前端 API 复用

继续复用已有接口：
- `getBrokerageWithdrawPage(...)`：列表展示
- `getBrokerageWithdraw(id)`：点击确认前拉取单条详情

不新增后端接口。

## 5.2 微信确认收款能力封装

在 `uniapp-marriage` 中新增一个轻量封装方法，用于统一调用微信小程序的确认收款能力。可参考 `uniapp-mall` 中的现有实现，但只引入当前页面所需的最小能力。

封装职责：
- 接收 `mchId` 和 `packageInfo`；
- 在微信小程序内调用 `wx.requestMerchantTransfer`；
- 对 success / fail / cancel 进行统一回调或 Promise 封装；
- 在非微信环境下直接给出错误。

建议放在 `utils/` 下独立工具文件，避免将平台判断和微信调用逻辑直接堆在页面里。

## 5.3 页面状态管理

提现记录页新增以下本地状态：
- 当前正在确认的提现记录 ID（防止重复点击）；
- 列表刷新中的 loading 状态继续沿用现有逻辑；
- 单条按钮 loading 与整页 loading 分开，避免一个按钮操作锁死整页。

## 5.4 刷新策略

确认收款返回后执行整页 `reload()`。

原因：
- 当前页面分页规模小；
- 整页刷新实现简单且稳妥；
- 可同时更新状态、按钮显隐与文案。

如果后续发现刷新延迟明显，再考虑补充“先同步转账单，再刷新列表”的增强方案；本次不强行扩展。

## 6. 平台约束

该能力仅适用于微信小程序。

因此实现上需要：
- 使用条件编译或运行时判断，仅在 `MP-WEIXIN` 可用场景展示按钮；
- 其它端不展示该按钮，避免出现无法完成的入口。

## 7. 错误处理

需要覆盖以下错误场景：

1. **详情接口失败**
   - 提示“获取提现详情失败，请稍后重试”；

2. **转账确认参数缺失**
   - 提示“当前记录暂不能确认收款，请稍后重试”；

3. **不在微信小程序环境**
   - 提示“请在微信小程序中确认收款”；

4. **用户主动取消**
   - 提示“已取消确认收款”；

5. **微信接口调用失败**
   - 优先展示微信原始错误信息；否则提示“确认收款失败，请稍后重试”；

6. **确认完成但列表仍是处理中**
   - 先执行页面刷新；
   - 若仍未更新，视为后端状态同步延迟，本次不在前端增加额外轮询逻辑。

## 8. 测试与验证

### 8.1 手工验证

至少验证以下场景：

1. 微信小程序中，微信零钱提现记录处于待确认状态，按钮正常显示；
2. 点击“确认收款”可成功拉起微信确认页面；
3. 用户确认后返回，列表自动刷新；
4. 用户取消后有明确提示，按钮恢复可用；
5. 非微信环境不展示按钮；
6. 参数缺失记录不会误触发确认；
7. 已成功/失败/审核拒绝的记录不展示确认按钮。

### 8.2 回归范围

- 提现记录页原有分页与加载状态不受影响；
- 申请提现页、钱包页、订单页无行为变化；
- 普通银行卡/二维码/支付宝提现记录无新增按钮。

## 9. 本次范围边界

本次只实现：
- 提现记录页展示“确认收款”按钮；
- 拉起微信确认收款；
- 操作完成后刷新列表状态。

本次不包含：
- 新增提现详情页；
- 自动弹出确认收款；
- 长轮询/定时轮询转账状态；
- 后端接口改造；
- 提现记录的更多字段展示优化。

## 10. 受影响文件（预计）

- `UI/uniapp-marriage/pages/distributor/withdraw-record/index.uvue`
- `UI/uniapp-marriage/utils/brokerage-api.uts`（如需补充更明确的类型/辅助方法）
- `UI/uniapp-marriage/utils/` 下新增或扩展微信确认收款工具文件

## 11. 实施摘要

最终实现路径为：

1. 在提现记录页识别“微信零钱 + 待确认/转账中”的记录；
2. 显示“确认收款”按钮；
3. 点击后拉取详情并读取 `transferChannelMchId` / `transferChannelPackageInfo`；
4. 调起微信 `requestMerchantTransfer`；
5. 返回后刷新提现记录列表。

# 红娘服务专属页设计说明

**日期：** 2026-06-26  
**范围：** `UI/uniapp-marriage` 前端专题页新增  
**目标：** 新增“红娘服务”专属页面，使用配置表读取“红娘服务”分类下的全部商品，展示专业可靠的平台官方风服务内容，并继续复用现有通用商品详情页完成商品浏览与下单链路。

## 1. 背景与现状

当前 `UI/uniapp-marriage` 已经存在多个围绕商品体系构建的专题页，核心模式一致：

- 商品详情统一走 `pages/product-detail/index.uvue`
- 商品列表通常通过商品分类或展示配置查询
- 页面层负责专题表达，交易链路复用商品、订单、支付现有能力

现有相关页面包括：

- `UI/uniapp-marriage/pages/member-packages/index.uvue`：会员套餐页，按会员配置中的分类查询商品
- `UI/uniapp-marriage/pages/emotion-academy/index.uvue`：情感学院页，先读取展示配置，再按分类查询商品
- `UI/uniapp-marriage/pages/activity/index.uvue`：活动页，先读取展示配置，再按分类查询商品
- `UI/uniapp-marriage/pages/product-detail/index.uvue`：通用商品详情页，承接商品浏览、规格选择、下单支付

本次新增“红娘服务”后，需要延续这套专题页模式：页面内容独立，商品与交易能力复用。

## 2. 产品目标

“红娘服务”页需要同时满足两类目标：

1. **表达目标**：建立“平台官方风”的专业、可靠、规范感，而不是单纯的商品陈列页
2. **业务目标**：展示“红娘服务”分类下全部商品，并允许用户进入通用商品详情页完成后续购买

页面整体结构采用“先讲服务，再上商品”的节奏，让用户先建立信任，再浏览服务商品。

## 3. 设计决策

### 3.1 选用方案

采用如下方案：

- **专属页面**：新增“红娘服务”专题页，而不是直接复用会员套餐页或活动页样式
- **配置表分类查询**：通过展示配置接口读取“红娘服务”专题所绑定的商品分类
- **复用通用商品详情页**：商品点击后继续跳转 `pages/product-detail/index.uvue`

### 3.2 不采用的方案

以下方案本次不采用：

- **直接复制会员套餐页**：虽然开发更快，但页面容易退化为纯商品列表页，专业感不足
- **直接套用活动页结构**：虽然接近“先介绍后展示”的节奏，但视觉表达仍不够专属
- **前端写死分类 ID**：后续配置变更需要重新发版，不利于运营维护
- **对商品再做二次分组**：用户已明确要求直接展示“红娘服务”分类下全部商品，不额外按档位、周期或人群拆分

## 4. 页面定位与风格

### 4.1 页面定位

“红娘服务”页是一个以平台官方风格展示婚恋顾问与牵线服务的专题页。它不是活动报名页，也不是课程页，而是强调：

- 平台提供规范化服务
- 服务过程可理解、可感知、可追溯
- 商品只是承接服务售卖的载体，页面先建立信任，再承接转化

### 4.2 风格要求

页面表达统一采用“平台官方风”：

- 文案语气稳重、规范、可信
- 避免过度营销化、煽动式表达
- 视觉延续现有婚恋项目的暖色、米白、深色文字体系
- 强调流程规范、实名审核、顾问跟进等信任要素

## 5. 页面信息架构

建议页面拆分为以下四个区块，自上而下展示：

### 5.1 顶部品牌介绍区

作用：在首屏快速传达“红娘服务”的官方定位。

建议内容：

- 页面标题：`红娘服务`
- 页面副标题：说明平台提供规范化婚恋顾问与牵线服务，帮助用户在真实、安心的前提下提升匹配效率
- 信任标签：2~3 个，突出官方服务特征，例如：
  - 实名审核
  - 顾问跟进
  - 流程规范

这一部分视觉上应优先体现正式、稳重，而非促销氛围。

### 5.2 服务说明区

作用：在展示商品之前先解释服务是什么、如何进行、适合谁。

建议拆成三个信息块：

- **服务保障**：说明平台提供规范流程、顾问服务、信息审核等保障
- **服务流程**：说明从沟通需求、匹配推荐到后续跟进的大致流程
- **适合人群**：说明哪些用户更适合选择红娘服务

该区域信息应当简明，不承载具体商品价格、SKU 或复杂业务规则，避免和商品详情重复。

### 5.3 商品列表区

作用：承接前面建立的信任，将用户引导到可购买商品。

设计要求：

- 直接展示“红娘服务”分类下全部商品
- 不在页面上额外做人群、服务档位、周期等二次分类
- 复用 `UI/uniapp-marriage/components/product-showcase-card.uvue`
- 商品点击后跳转通用商品详情页

商品区需要有明确的小标题或承接文案，例如“可选服务”或“服务商品”，但不需要过多营销化描述。

### 5.4 底部说明区

作用：补充页面边界说明，避免专题文案与商品内容不一致。

建议文案方向：

- 具体服务内容以商品详情说明为准
- 服务安排、权益范围、适用条件以实际商品信息为准

这部分用于收口页面预期，减少用户误解。

## 6. 数据来源与查询逻辑

### 6.1 展示配置读取方式

红娘服务页不直接写死分类 ID，而是通过展示配置接口读取配置：

- 接口：`/product/display-config/get?sceneCode=...`
- 页面使用固定场景码：`matchmaker_service`

前端启动流程：

1. 页面加载时先请求展示配置
2. 读取配置中的 `categoryIds`
3. 取第一个分类 ID 作为红娘服务商品分类
4. 再请求该分类下的商品列表
5. 页面展示商品卡片

这样后续如果“红娘服务”分类发生变更，可以通过配置表调整，而不需要修改前端代码。

### 6.2 商品列表获取方式

商品列表继续使用现有商品分页接口：

- 接口：`/product/spu/page`
- 条件：`pageNo=1&pageSize=20&categorySales=<分类ID>`

是否需要继续逐个拉取详情，取决于当前项目的专题页实现模式。考虑到活动页和课程页已有按现有商品详情结构补全展示字段的做法，红娘服务页应优先复用同样的方式，保证卡片所需字段完整、表现一致。

### 6.3 商品详情跳转

商品点击后继续复用已有通用商品详情页：

- 页面：`UI/uniapp-marriage/pages/product-detail/index.uvue`
- 跳转参数：`/pages/product-detail/index?id={spuId}`

本次不新增独立的红娘服务详情页，不改动商品详情、订单、支付、分销链路。

## 7. 建议代码结构

### 7.1 新增页面

新增页面文件：

- `UI/uniapp-marriage/pages/matchmaker-service/index.uvue`

职责：

- 渲染平台官方风顶部介绍与服务说明
- 调用展示配置接口获取红娘服务分类
- 查询该分类下的商品列表
- 处理加载态、空态、异常态
- 点击商品跳转通用商品详情页

### 7.2 新增 API 文件

新增轻量数据访问文件：

- `UI/uniapp-marriage/utils/matchmaker-service-api.uts`

职责：

- 定义页面所需的商品类型
- 提供展示配置读取方法
- 提供红娘服务商品查询方法
- 视需要复用现有活动页/课程页的数据结构与详情补全逻辑

### 7.3 路由注册

需要在：

- `UI/uniapp-marriage/pages.json`

中注册 `pages/matchmaker-service/index` 页面，保持和现有自定义导航页面一致的 `navigationStyle: custom`。

## 8. 交互与状态设计

### 8.1 加载态

页面初次进入时：

- 顶部静态介绍可先直接展示
- 商品区展示“加载中”状态
- 同时可继续沿用 `uni.showLoading` 提供全局加载反馈

这样页面不会在首屏出现空白，视觉上更稳定。

### 8.2 配置未设置

当 `sceneCode = matchmaker_service` 查询不到有效配置，或 `categoryIds` 为空时：

- 标题：`暂未配置红娘服务`
- 说明：`请在商品展示配置中绑定“红娘服务”分类后再试`

这是运营配置缺失态，不应误导用户为普通网络异常。

### 8.3 分类已配置但无商品

当分类存在，但该分类下暂无已上架商品时：

- 标题：`暂无可选红娘服务`
- 说明：`当前分类下暂无已上架商品，请稍后再来查看`

这是内容空态，语气应平稳，不带错误色彩。

### 8.4 接口失败

当展示配置接口或商品接口失败时：

- 标题：`加载失败`
- 说明：`网络异常或服务暂不可用，请稍后重试`
- 交互：建议提供重新加载入口
- 反馈：可以保留 `uni.showToast({ icon: 'none' })` 提示用户加载失败

### 8.5 返回行为

返回逻辑可沿用现有专题页模式：

- 优先 `navigateBack`
- 失败时回退到合适入口页（通常是 `mine` 或首页）

具体跳转兜底路径可以参考现有会员套餐页和活动页的实现风格，保持一致。

## 9. 复用边界

### 9.1 继续复用的能力

以下能力继续复用，不重复建设：

- 通用商品详情页：`pages/product-detail/index.uvue`
- 商品展示卡片：`components/product-showcase-card.uvue`
- 展示配置接口：`/product/display-config/get`
- 商品分页接口：`/product/spu/page`
- 既有订单、支付、分销链路

### 9.2 红娘服务页独立维护的内容

以下内容由红娘服务页自行维护：

- 平台官方风顶部文案
- 服务保障 / 服务流程 / 适合人群内容
- 专属空态与异常态文案
- `matchmaker_service` 这一场景码常量

这意味着：**商品交易能力通用，专题表达独立。**

## 10. 本次不做的内容

为了保持范围清晰，本次不包含以下内容：

- 不新增后端商品详情链路
- 不新增独立红娘服务订单类型
- 不新增红娘服务独立商品详情页
- 不做商品二次筛选、排序器或复杂标签系统
- 不抽象统一的“专题商品页基类”或复杂公共查询工具

当前项目已有 `member-api.uts`、`activity-api.uts`、`course-api.uts` 等页面级 API 文件，本次新增 `matchmaker-service-api.uts` 更符合现状，风险也更低。后续如果多个专题页模式稳定一致，再统一抽象。

## 11. 成功标准

当以下条件同时满足时，本次设计视为成功：

1. 用户可以进入“红娘服务”专属页
2. 页面首屏先展示平台官方风服务介绍
3. 页面能通过配置表读取“红娘服务”分类
4. 页面能展示该分类下的全部商品
5. 商品点击后成功进入通用商品详情页
6. 页面能正确区分并展示加载态、未配置、无商品、加载失败等状态
7. 页面整体视觉与文案体现专业、可靠、规范的官方风格

## 12. 实施建议

实施时应尽量贴近现有 `emotion-academy` 与 `activity` 页面模式：

- 页面负责内容与状态组织
- API 文件负责配置与商品查询
- 商品卡片与详情页继续复用

这样可以在不扰动现有交易链路的前提下，快速扩展出新的“红娘服务”专题页，并保留后续运营通过配置表调整分类的能力。

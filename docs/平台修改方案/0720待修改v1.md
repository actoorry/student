## 客商中心（partner）

### partner关联文件

**现状**：客商文件（背景图、相册、头像、简历）分散存储在 `partner` 表字段或 `infra_file` 表中，未统一管理，缺少类型区分和默认选项。

**修改**：新建 `partner_rel_file` 表，统一管理客商关联文件。

**表结构**：

| 字段 | 类型 | 必填 | 说明                                                 |
|------|------|------|----------------------------------------------------|
| partner_id | bigint | ? | 客商ID，FK → partner.id                               |
| file_id | bigint | | 文件ID，FK → infra_file.id（优先引用统一文件表）                 |
| type | varchar(50) | ? | 文件类型，数据字典 `partner_file_type`（背景图/用户相册/用户头像/用户简历等） |
| is_default | tinyint | ? | 是否默认：0=否 1=是。同一 `type + partner_id` 组合下只能有一条默认     |
| sort | int | ? | 排序，越小越前                                            |
| remark | varchar(500) | | 备注                                                 |

**设计要点**：

| 要点 | 说明 |
|------|------|
| 多对多 | 一个客商可有多个同类型文件（如多张相册），一个文件也可关联多个客商 |
| 类型区分 | `type` 字段引用系统字典，不同字典值互不影响 |
| 默认选项 | 每种 type 下可有且仅有一条 `is_default=1`，前端默认展示该条 |
| 排序 | `sort` 控制同 type 下的展示顺序 |
| 文件存储 | 本表仅做关联引用，文件实体统一存储在 `infra_file` 表 |

**原 partner 表涉及字段**：

| 原字段                    | 迁移方式 |
|------------------------|---------|
| `avatar`（头像URL）        | 迁移到 partner_rel_file，type=`avatar`，is_default=1 |
| `background_img` 等     | 迁移到 partner_rel_file，type 取字典 `partner_file_type` 对应值 |
| 其他零散与file关联的字段，婚恋模块相册等 | 按语义迁移到对应 type |

### product关联类别

**现状**：`product_spu` 表中 `category_sales`（bigint）和 `category_store`（bigint）各存一个分类ID，仅支持一对一分类。实际业务中一个产品可能属于多个销售分类或多个仓储分类。

**修改**：新建 `product_rel_category` 表，支持多对多分类关联。废弃 `product_spu.category_sales` 和 `product_spu.category_store`。

**表结构**：

| 字段 | 类型 | 必填 | 说明                                            |
|------|------|------|-----------------------------------------------|
| spu_id | bigint | ? | 产品SPU ID，FK → product_spu.id                  |
| category_id | bigint | ? | 分类ID，FK → product_category.id                 |
| type | varchar(50) | ? | 分类类型，数据字典 `product_category_type`（销售分类/仓储分类等） |
| is_default | tinyint | ? | 是否默认：0=否 1=是。同一 `type + spu_id` 下只能有一条默认      |
| sort | int | ? | 排序，越小越前                                       |
| remark | varchar(500) | | 备注                                            |

**设计要点**：

| 要点 | 说明 |
|------|------|
| 多对多 | 一个产品可关联多个销售分类 + 多个仓储分类 |
| 类型隔离 | `sales` 和 `store` 独立管理，互不干扰 |
| 默认分类 | 每种 type 下 `is_default=1` 的唯一一条作为主分类，前端默认展示 |
| 迁移策略 | 旧数据先 INSERT 到 product_rel_category，验证无误后再 DROP 旧字段 |

**原 product_spu 涉及字段**：

| 原字段 | 迁移方式 |
|--------|---------|
| `category_sales` | INSERT INTO product_rel_category(type='sales', is_default=1) → DROP COLUMN |
| `category_store` | INSERT INTO product_rel_category(type='store', is_default=1) → DROP COLUMN |

## 三、客户关系（crm ）

### 3.1 整体业务流程

```
线索录入 → 转为客户 → 完善客户数据 → 报价/公海
                                    │
                                    ├── 客户意向高 → 新建报价单（销售订单）
                                    │       └── 报价确认 → 转正式销售订单 / 转合同
                                    │
                                    └── 客户无意向 → 放入公海
                                            └── 销售人员领取 → 从公海移除
```

### 3.2 线索管理

- 录入线索数据
- 确认是有希望的客户，或数据相对完整后，把**线索数据转换到客户数据**
- 目前线索数据转为客户报错

### 3.3 客户管理

- **新增客户完成后，需要展示客户数据**（当前新增完成无展示）
- **负责人字段下拉框**：应取 `system_users` 中标记为"销售"的用户
- **移除联系人功能 相关代码**（不再维护联系人子表），客户就是联系人，如果需要下级，也是使用partner_rel_partner来表达即可
- 客户数据完善 + 意向高 → 可新增报价管理
- 客户没有归属的销售，则在客户公海中展示
- 客户无意向 → 放入公海

### 3.4 客户公海

- **修复**：销售人员无法领取客户
- **修复**：领取公海客户后，公海列表不再展示已被领取的客户

### 3.5 合同管理

- 合同中记录**甲方、乙方、总金额**，不需要明细记录 → **移除合同明细数据**
- 合同中记录 **origin_id 号**，用于跨单据串联
  - 合同有可能是销售订单转过来的，需要使用origin_id 记录源单据ID
- no 字段：订单流水号，全部都从 基础服务清单中获取
  - id是雪花主键，方便机器识别，no号是日期主键方便人员识别

### 3.6 origin_id 号机制（全局串联号）

**定义**：origin_id 是系统为各单据关联生成的唯一号码，贯穿整个业务流。

> **原则**：谁先创建谁生成 单据id ，则origin_id=当前id，当单据传送或者派生而来，都记录原有的origin_id。
> 
```
场景1：销售订单 → 出库单 / 采购订单 / 合同
  销售订单新建时 origin_id → 后续单据使用销售订单的 origin_id

场景2：合同 → 销售订单
  合同新建时 origin_id → 关联新建销售订单时使用合同的 origin_id
```

## 五、销售订单（sales）

参考 yudao 开发文档：`http://qyg.proxy.iyxiang.com:1921/yudao-docs/index.html`
### 5.1 Status 字段拆分
**删除商机管理代码**，改用**销售订单**替代，通过菜单参数区分"报价单"视图。
- 通过菜单引导到销售订单界面
- 菜单中配置参数（如 `status=quotation`），让页面知道是报价状态模式

将原来的 `status` 字段拆分为 **3 个独立字段**：

| 字段 | 说明 | 职责                           |
|------|------|------------------------------|
| `status` | 订单状态 | 表达订单生命周期（草稿/报价单/已审核/已完成/已取消） |
| `delivery_status` | 配送状态 | 所有物流相关判断使用此字段（待发货/已发货/已签收）   |
| `pay_status` | 付款状态 | 所有支付相关判断使用此字段（待付款/已付款/已退款）   |

前端小程序的订单状态也要修改成三个

> **原因**：一个销售订单即使没有付款也有可能发货。发货、付款、订单状态应该独立管理。

### 5.2 销售订单 → 合同

- 销售订单可**同步至合同**（仅头信息，不同步明细）
- 销售订单可**关联已有合同**

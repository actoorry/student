# 婚恋交友平台 V1 技术落地方案

## 1. 文档目的

基于 PRD《婚恋交友平台 V1.0 产品需求文档》和当前改造后的 suxin-pro 工程现状，输出婚恋域模块拆分方案、表设计草案、V1 接口清单与开发排期，作为后续详细设计和开发实施依据。

## 2. 当前技术结论

当前工程具备婚恋平台 V1 落地所需的大部分基础底座，整体可行，但不能采用“在现有 `partner/member` 上持续堆字段”的方式推进。

建议采用：

- 复用现有身份、支付、分销、权限、IM、通知基础能力
- 在 `suxin-module-system` 下新增婚恋业务子域 `dating`
- 将婚恋特有能力通过独立扩展表建模
- 通过统一状态机和业务门禁控制实名、聊天、风控、分销等行为

## 3. 模块拆分方案

### 3.1 总体原则

- 所有业务代码继续放在 `suxin-module-system`
- 不新增独立 Maven 模块
- 沿用现有 suxin-vue-pro 分层规范
- 通用主档与婚恋业务扩展解耦

### 3.2 模块划分

#### 3.2.1 `member` 域

继续作为会员主档域，负责通用会员身份能力。

复用内容：

- `member`
- `partner`
- `system_users`

职责边界：

- 注册来源
- 等级、积分、分组、通用标签
- 基础会员身份

不承载内容：

- 婚恋择偶条件
- 实名审核明细
- 相册审核
- 点赞匹配
- 聊天券
- 活动报名

#### 3.2.2 新增 `dating` 域

建议包前缀：

`vip.appap.suxin.module.dating`

建议继续拆分子域：

- `profile` 档案
- `verify` 实名认证
- `match` 点赞匹配
- `chat` 聊天券与聊天授权
- `activity` 活动
- `risk` 举报与风控
- `merchant` 商家、红娘、线索、公海、跟进

#### 3.2.3 `im` 域

继续作为消息基础设施层复用。

复用内容：

- `im_private_message`
- `im_friend`
- `im_sensitive_word`

职责边界：

- 消息存储
- 会话基础能力

不负责内容：

- 是否允许发起私聊
- 是否需要消耗聊天券
- 是否已经解锁自由聊

以上能力统一放在 `dating.chat` 做业务校验。

#### 3.2.4 `sales.trade.brokerage` 域

继续作为分销返佣与提现底座复用。

复用内容：

- `trade_brokerage_user`
- `trade_brokerage_record`
- `trade_brokerage_withdraw`

补充内容：

- 锁客保护期
- 商家维度佣金规则
- 来源用户实名后发券逻辑
- 婚恋业务特定结算规则

#### 3.2.5 `accountant.pay` 域

继续做支付与钱包底座。

复用内容：

- `pay_wallet`
- `pay_wallet_transaction`
- `pay_order`
- `pay_refund`

承接业务：

- 会员套餐支付
- 活动报名支付
- 钱包余额
- 提现相关资金能力

#### 3.2.6 `crm` 域

只建议部分参考，不建议直接强耦合。

可参考能力：

- 线索公海
- 跟进记录
- 数据分析

建议：

婚恋业务下新增独立商家与红娘线索体系，必要时通过桥表或服务层与现有 CRM 联动。

## 5. 用户状态设计建议

不建议只依赖 `partner.status` 单字段控制全链路状态，建议拆为多维状态：

- 账号状态：启用/停用
- 婚恋接入状态：游客/S1 注册/S2 实名/S3 风控冻结
- 实名状态：未提交/审核中/通过/拒绝
- 档案状态：未完善/待审核/已上架/已下架
- 聊天权限状态：不可发起/可发破冰/已自由聊

这样可以避免业务逻辑散落在各个接口中通过 if/else 临时判断。

## 7. V1 开发排期

建议按照 12 周执行，分为 4 个阶段。

### 7.1 阶段一：基础链路，2 周

工作内容：

- 会员登录改造为真实 OAuth2 token
- 梳理 App 用户类型与鉴权链路
- 建立 `dating` 基础包结构
- 建立核心字典、枚举和错误码
- 输出第一版 DDL

交付物：

- 可登录的 C 端认证链路
- 基础表落库
- 初版菜单与权限

### 7.2 阶段二：核心婚恋能力，3 周

工作内容：

- 档案主表、择偶条件、相册
- 实名提交流程
- 推荐列表、搜索列表
- S1/S2 状态门禁
- 访客、点赞、互赞

交付物：

- 可注册
- 可实名
- 可浏览用户
- 可点赞匹配
- 后台可审核实名与相册

### 7.3 阶段三：聊天与分销，3 周

工作内容：

- 聊天券账户与流水
- 破冰消息规则校验
- 互赞/回复解锁自由聊
- 180 天锁客关系
- 预估收益/T+7 结算
- 提现申请

交付物：

- 可控聊天能力闭环
- 拉新分销闭环
- 提现闭环

### 7.4 阶段四：活动与 B 端运营，4 周

工作内容：

- 活动发布、报名、支付、核销
- 商家端、红娘端线索与跟进
- 商家佣金规则
- 风控举报处理
- 首页运营配置

交付物：

- B2B2C 基础闭环
- 商家端、红娘端、平台端可运行

## 8. 优先落地的三条主链路

V1 最重要的不是功能铺满，而是打通三条核心主链路：

### 8.1 用户链路

注册 -> 完善档案 -> 实名 -> 推荐/点赞

### 8.2 社交链路

互赞/聊天券 -> 破冰 -> 解锁聊天

### 8.3 交易链路

拉新绑定 -> 支付 -> 预估收益 -> T+7 -> 提现

## 9. 需要尽快确认的技术决策

### 9.1 手机号与身份证存储策略

建议：

- 手机号：密文 + 检索哈希 + 展示脱敏
- 身份证号：密文 + 检索哈希 + 展示脱敏

说明：

- 如果手机号需要登录、查重、检索，不能只做不可逆存储
- 需要在合规要求和业务检索能力之间取得平衡

### 9.2 商家隔离模型

建议：

- V1 采用“平台单租户 + 商家维度 + 数据权限”

不建议：

- 一开始直接做系统级强租户隔离

原因：

- PRD 存在平台统一公海、全局风控、全局审核与统一分销规则
- 强租户会显著提高模型复杂度和跨商家协同成本

## 10. 最终结论

婚恋交友平台 V1 在当前改造后的 suxin-pro 上具备明确落地可行性。

最优路径不是重做底座，而是：

- 复用现有身份、分销、支付、IM、权限体系
- 在 `suxin-module-system` 下新增 `dating` 业务域
- 用扩展表承接婚恋特有模型
- 用统一状态机和业务门禁保障实名、聊天、风控、结算等关键链路

后续建议优先输出：

1. 第一版 DDL 明细
2. 后端包结构与菜单权限命名方案
3. 接口字段级设计
4. 前后端页面与角色权限矩阵
